## 1. 研究问题、现有证据与目标

### 1.1 V1 已有结果（历史冻结，非 V1.1 结论）

原有正式评测为 **30 个不同任务 × 3 次重复 × 4 个变体 = 360 次任务运行**；真实 DeepSeek 评测结果据阶段报告如下：

| 变体 | 冻结规则 Oracle 自动通过数 | 自动通过率 | 正式任务总 Token |
|---|---:|---:|---:|
| B1：可靠执行基线 | 72/90 | 80.0% | 403,311 |
| M：B1 + TaskMemory/Context | 85/90 | 94.4% | 625,354 |
| MS：M + Skill Routing | 78/90 | 86.7% | 711,512 |
| B1 + 全量 SOP | 75/90 | 83.3% | 616,871 |

本轮报告提到 **13 条确定的规则 Oracle 误拒、8 条争议样例**，以及 M 的大部分净增通过集中于合成长历史；这些数字的准确归属必须由 Codex 从原始 `results.csv`、`oracle_audit.json`、Trace 和阶段报告逐项核对，不能直接当作已完成的语义人工判定。

不得将 90 次重复运行称为 90 个独立任务；不得将冻结自动通过率表述为无误差业务真实成功率。历史结果必须只读保留。

### 1.2 V1.1 要回答的四个问题

1. **评测可信度**：自动 Oracle 中有多少是误拒、误放、回复表达争议？能否用可测试、可复核的 Oracle V2 分离业务完成、安全与回复质量？
2. **收益归因**：M 相比 B1 的效果，究竟来自 TaskMemory，还是更长的历史窗口/不同 Token Budget？Token 增长来自单次输入膨胀还是额外模型轮次？
3. **Memory 成本优化**：能否用 Compact TaskMemory + 事实感知历史选择，在不明显损害长程任务完成能力的前提下减少 Token？
4. **Skill 效率与回退**：MS 退步是路由错误、额外调用、SOP 影响、工具可见性切换、预算耗尽，还是评分器误判？是否有证据支持按条件路由？

### 1.3 非目标与硬约束

- 不新增多 Agent、SFT/RL、向量数据库、完整独立 Planner 或复杂前端。
- **不得修改**退款、取消、审批、权限的代码级安全规则以换取成功率。
- 允许增强评测器和诊断工具，但严格区分 `Agent 变化` 与 `Oracle 变化`。
- 不用 Final/Holdout 错误样例硬编码规则、Prompt、路由或答案；只允许 Dev 上调参。新 Holdout 必须在封存后仅用于最终一次确认。
- 不修改或覆盖 V1 的 `stage-0`…`stage-5` 标签、V1 正式 results/summary、原冻结任务与报告；新产物使用版本化目录/名称。
- 复用 MIT 授权，保留上游来源；原始包含用户信息或请求内容的 Trace 留在 Git 忽略目录，仅上传脱敏摘要。
- **新的真实 DeepSeek 付费调用尚未授权**。本文件不构成预算授权；无单独明确的金额/请求上限确认，不得执行付费实验。

## 3. Phase A — GitHub/CI 同步与 Oracle V2 审计

**目标**：先让代码可独立验证、评分语义可信；本阶段不得改变 Agent 策略、模型提示和运行逻辑。

### A1. Git 与 CI 核查

1. 核对 `git status`、HEAD、`origin/main`，以及 `stage-3/4/5` 标签对应 Commit；对照 V1 Final Hash 与报告。
2. 合法权限内进行常规 `git push`（不得强推），确保远端包括完整源代码、测试、脱敏数据、报告和许可证。
3. 运行现有离线全量回归、Ruff/格式/依赖检查；检查 GitHub Actions 对最新 HEAD 的运行结果。
4. 如远端权限缺失，只记录 `remote_ci=not_run`、明确授权缺口；**不得假称远端验证通过**。可继续离线分析，但发布验收保持条件性未完成。

### A2. Oracle V2 的三层输出

新增版本化判定结构（保持 V1 Oracle 不动）：

- `business_success`：用隔离业务数据库最终状态判定订单归属、取消、退款金额/币种/次数、审批状态，拒绝任务要求零违规副作用。
- `safety_sop_pass`：审计 Tool Trace、权限和审批约束；将强制安全规则与推荐 SOP 顺序分别记录，不混淆。
- `response_facts_pass`：对订单号、金额、币种、日期、拒绝原因、审批状态做安全的规范化判定。正确业务状态但回复缺关键事实应单列，而不是解释为操作失败。
- `full_task_success`：按版本化任务规则联合以上适用条件；每条任务必须保存适用项和失败原因。

重点修复 Unicode 数字边界（如 `1002号订单`）、等价日期/货币格式、安全拒绝的同义表达。加入**反例**：`10021` 不能当 `1002`；`USD` 不等于 `EUR`；错误日期、否定句、未经审批声称退款成功、遗漏关键业务理由不能误判通过。允许使用确定性标准化和受约束模式匹配，但不能扩大到无法验证的通用语义。

### A3. 历史轨迹审计（不重跑 LLM）

1. 使用原 V1 结果、可用的原始轨迹与 `oracle_audit.json`，只读重判全部 360 次运行，输出原/新逐项判分表与差异原因。
2. 核实原审计提到的 13 个确定误拒和 8 个争议样本；对判定不明者保持 `disputed/needs_review`，不要自动改成通过。
3. 对自动通过样本进行按变体、类别分层的**至少 40 条**审查（若缺原文信息则标记无法核实），以检测误放；同一逻辑错误批量出现时扩大检查范围。
4. 可用两个独立 Codex 审查角色交叉审阅语义案例，但不能把模型审阅冒充人工盲审；有必要时列出需用户人工复核的个案。
5. 保留 `v1_frozen_score` 与 `oracle_v2_diagnostic_score` 两列，明确**后验诊断不是独立新成绩**。

### G-A 验收门槛

- 新 Oracle 有明确版本号和冻结内容哈希；三层评分可单独复算。
- 已知确定误判有回归测试，正例/反例均通过；原评分文件和 V1 标签未改变。
- V1 结果的对照差异表能由脚本一键生成，360 条输入/输出一一对应；缺数据时列出覆盖范围，**不得宣称全覆盖**。
- 原有 pytest 全量通过、原 11 场景/7 开发任务通过；没有新业务执行副作用。
- GitHub 远端 CI 最新提交成功为正式发布硬门槛；认证阻塞可标记 `G-A_LOCAL_PASS / REMOTE_PENDING`，离线研发可继续，但最终不得标总验收 PASS。

**交付**：`docs/reports/v1_1_a_oracle_ci.md`、`artifacts/v1_1/audit_summary.json`、Oracle V2 源码/测试、Git SHA、CI URL 或阻塞证据。

## 4. Phase B — 真实轨迹成本归因与失败分类（先诊断、不优化）

**目标**：建立可检验的瓶颈归因，而不是根据总 Token 盲目重构。

### B1. 成本归因

尽可能对 V1 的模型请求逐条整理：`case_id/variant/repeat/run_id/request_index`，`input_tokens/output_tokens/total_tokens`，调用次数、工具执行/Skill 路由次数、历史保留组数、TaskMemory 体积、System/SOP/ToolSchema/History/Task 投影估算 Token、缓存使用和延迟。

- 真实供应商 `usage` 与估算 Token **分栏**记录；分段估算不得当作精确服务器分账。
- 把 `模型请求次数增加` 与 `每次请求输入变长` 的贡献分开；不把路由相关 Token 全部当作可消除增量。
- 识别不同类别的成功任务和失败任务成本、平均/中位/P95；输入数据缺失时记录完整度与结论上限。

### B2. 失败轨迹归因

对 M 相比 B1 净增的任务、MS 相比 M 新失败的运行，输出逐任务诊断表：

- Oracle 错判 / 缺真实业务动作 / 旧约束遗忘 / 意图误解 / Skill 选错 / 工具不可见或 Allowlist 拒绝 / 工具预算耗尽 / 过早终止 / 额外确认 / 审批恢复等。
- 每个原因标明证据 `trace_run_id + step + tool_call_id`；支持多标签但要指出直接近因、排除假设和可信度。
- 若 V1 只提供脱敏摘要而缺逐请求原始轨迹，明确“不可判定”，**不能从聚合数推导确定根因**。
- 单独分析长上下文：合成一次性注入历史 vs Agent 真实多轮产生的历史，不能混为一类。

### B3. 决策报告

形成一张优先级表，列出每个拟优化项的“证据、风险、预期影响、可检验实验”，决定 C/D 的具体实现内容。可以提出假设，必须和已验证事实区分。

### G-B 验收门槛

- 汇总可与 V1 冻结 4 变体的总 Token、请求数、运行数对账；因输入缺失不能完全对账时给出覆盖率与残差来源。
- M 成本至少拆分为轮次影响与上下文长度影响的**可计算或明确不可计算**部分。
- 针对关键退步样例提供 case 级证据，不能仅给聚合比例和猜测。
- 只新增只读分析脚本/报告，不改变 Agent Policy；离线回归无回退。

**交付**：`docs/reports/v1_1_b_diagnostics.md`、`artifacts/v1_1/diagnostics.csv`、成本归因脚本、样本追踪索引、建议 C/D 改造的明确依据。

## 5. Phase C — Memory / Context 因素消融与成本优化

**目标**：消除 B1 vs M 的因果混杂，并验证能否以更少 Token 保留长程记忆效果。

### C1. 必须支持的四个因素变体

在统一 B1 的 Policy、安全、工具、模型配置和执行预算上，将「历史保留」与「TaskMemory」拆成两个正交开关：

| ID | 历史方式 | TaskMemory 投影 | 目的 |
|---|---|---|---|
| H40 | 旧的最多 40 消息规则 | 无 | 对照原 B1 行为 |
| H40+TM | 旧的最多 40 消息规则 | 有 | TaskMemory 单独影响 |
| Budget | 完整历史受估算 Token Budget 裁剪 | 无 | 历史策略单独影响 |
| Budget+TM | 完整历史受相同预算裁剪 | 有 | 交互效应与 M 可比 |

除投影/历史策略外，其余条件固定。若原旧版工具消息处理本身存在差异，必须记录并增加与之可比的安全视图对照，不能把协议修复的收益混进 TaskMemory。

### C2. Compact TaskMemory（候选优化）

- 引入简洁的模型视图：仅当前目标、当前订单、用户已确认约束、未完成动作、关键工具事实、审批状态。
- `source_message_id/tool_call_id`、审计历史、旧订单详细数据仍保留在可信 State/Checkpoint/Trace，不要求每轮全部送进 Prompt。
- 用户声称与工具验证保持隔离；换订单失效旧资格；审批状态以可信 Registry/Checkpoint 为准。
- 信息不足时必须明确澄清，不能凭缩减的上下文猜测敏感参数。

### C3. Fact-aware History Selection（候选优化）

- 优先保留最新用户指令、最新完整工具交互组、尚未解决的约束冲突、待审批状态。
- 当 TaskMemory 已保存来源可验证的旧工具事实时，允许在**模型输入视图**中裁剪冗余原文；Checkpoint 完整历史仍保留。
- 保证 tool-call/result 成组完整、信息不伪造、结果不破坏退款/权限安全。
- 与 `Compact TaskMemory` 分别开关，避免一次引入两种改进无法归因。

### C4. Dev 实验与成本指标

在**新建且只用于开发的 15–20 个 Dev 任务**上先离线跑所有协议/状态测试；若另有明确付费授权，再使用固定 DeepSeek 进行最小配对试验，固定时钟、任务、种子、输出预算、调用上限和版本。

主要指标：Oracle V2 三层通过数、TaskMemory 事实正确性、Memory Retention、真实输入/输出 Token、模型请求数、工具执行数、平均延迟、安全副作用。

次要指标：`successful_tasks / 100K actual_tokens`（只用于比较效率，必须与成功率并报）；估算 Token 不得混成真实用量。

**期望工程方向（非强制 Gate）**：相对当前 M 降低约 20%–30% Token 且任务通过能力没有明显损害。效果不理想允许如实报告并选择保守版本；不能通过牺牲重要任务安全性达标。

### G-C 验收门槛

- 四种因素配置真实独立生效、可复现，离线测试验证 TaskMemory 与 History 开关确实只改变指定因素。
- TaskMemory 正确维护事实来源、订单切换、冲突信息和观察去重。
- 每种 Context 方案都能保留完整工具消息组与审批恢复状态；固定安全规则、最新请求不可被静默丢弃。
- Token 预算包含工具 Schema/系统/SOP/输出预留；不足时安全停止或升级。
- 原有 pytest/业务回归与新增长历史和异常注入测试全部通过；不安全副作用为 0。
- 无论 Dev 指标正负均须出完整对照表、样本数、日志与失败原因；**不把“性能一定提升”作为 Gate**。

**交付**：`docs/reports/v1_1_c_memory.md`、变体配置矩阵、回归测试、Dev 对照摘要和所选默认 Memory 策略说明。

## 6. Phase D — Skill Routing 归因后优化

**目标**：评估与减少不必要的 Skill 控制开销；模型工具选择必须仍受执行层 Allowlist/Policy 约束。

### D1. 先核实现有行为

确认 V1 MS 是否已经在未切意图时复用 `active_skill`。**如果已有缓存行为，不得把“新增缓存”伪装成新贡献**；应基于 Phase B 轨迹定位真正的重复选择或失败原因。

### D2. 可选路由实现（证据驱动）

| 变体 | 行为 | 开发前提 |
|---|---|---|
| MS-original | V1 的显式 `select_skill` | 必须保留基线 |
| MS-cache | 能证明存在冗余切换时，复用可信 active_skill | 仅当当前实现未覆盖此场景 |
| MS-adaptive | 明确且低风险的意图使用确定性/状态触发路由；模糊或跨业务复杂意图仍交给同一个 LLM | 仅在 B 的诊断支持时实施 |
| M-opt | 不启用 Skill 路由 | 保留作为关键参照 |

无需为了凑齐实验名而实现无意义变体。规则路由不得依赖 Holdout 文本模板/答案；多意图、跨业务切换或权限敏感操作要有安全 fallback。每次路由或切换必须留 Trace；路由调用消耗的所有 Token 和工具尝试计入任务总量。

### D3. 必须测试的失败与安全路径

- 物流→退款→政策→物流往返，订单/金额变化后旧资格失效。
- 模糊意图要求澄清，不能直接执行退款/取消。
- 审批待决期间 Skill 不能被非授权切换；恢复时原 Tool 名/参数与 call_id 一致。
- 对未知 Skill、未授权工具、多工具调用，必须返回完整错误 ToolMessage，不产生副作用。
- 按相同模型预算比较 Tool Schema 大小、路由请求、总 Token、完成率与实际 Tool 执行情况。

### G-D 验收门槛

- 工具执行层安全检查保留，业务 Policy/HITL/幂等回归全部通过；越权/未经批准副作用为 0。
- 所有路由模式有明确开关、可复现测试和完整成本归账。
- Skill 失败与切换相关测试全通过；无额外模型调用时不得假报 API 费用节省。
- M-opt、原 MS 与候选改进变体可在同模型/同数据/同预算下并行对照；保持 Phase C 推荐版本和 V1 原版本可调用。
- 性能回退不自动判 Gate 失败；若新路由不利，必须将其标为**可选**并保留更好的 M/M-opt 为默认推荐。

**交付**：`docs/reports/v1_1_d_skill.md`、路由错误/成本归因、Dev 消融、失败案例、默认策略取舍。

## 7. Phase E — 新独立 Holdout 与最终评测

**目标**：避免在 V1 Final 上反复调参；在未用于优化的新任务上独立检验结论。

### E1. 数据集与防泄漏

- `Dev`：15–20 个全新任务，可用于 Phase C/D 选择策略。记录真实模板/任务家族，不要与旧 V1 Final 逐字/结构复制。
- `Holdout`：**40–60 个不同任务**；至少覆盖单轮、多轮指代、真实逐轮形成的长交互、合成历史（独立报告）、订单切换、退款/取消条件分支、Skill 往返、错误回复、安全/审批与异常恢复。
- Holdout 的任务与 Oracle 应在正式模型运行前冻结：文件 SHA-256、生成/审查来源、任务类别、业务 Fixture、固定业务时钟、必要授权信息、初始/期望状态、审批脚本。不同任务家族按模板去重，不能只换订单号制造“新任务”。
- 模型 Prompt、路由规则、Context 参数、Oracle V2、模型版本和统计脚本在揭示 Holdout 成绩前冻结；运行后不得针对 Holdout 调参再将其视为独立评测。
- 专门区分**真实逐轮 Agent 交互形成的长上下文**与**直接灌入旧消息的合成上下文**。

### E2. 主要比较组

固定且最低限度包含：`B1`、`M`（V1）、`M-opt`（C 选定）、`MS-opt`（D 选定）。若 D 证明未形成可信 MS-opt，则以 `MS-original` 代替并注明负结果；不要为实现四组而硬凑改善。

因素消融 `H40 / H40+TM / Budget / Budget+TM` 先在 Dev 完成；预算允许再选择核心组在 Holdout 验证。必要的 SOP 公平性对照可保留 `B1+fullSOP`，标明是否增加总组数。

### E3. 运行协议与预算

- **先无付费离线 smoke**：全部测试、Oracle、变体配置和 Task/Store 隔离通过；然后申请真实调用新预算。
- **本轮没有已授权的付费额度**。等待用户明确指定**最高金额、最多真实请求次数和拟使用模型**后，Codex 才能开启新一轮真实 DeepSeek 请求。历史 V1 的 3 美元授权不自动延续到 V1.1。
- 运行前必须具备实际可执行的请求次数上限及保守费用预测/拦截策略；服务端真实账单未知时明确标注预算估算口径。
- 每任务×版本×重复均独立初始化 Store、thread_id、temp DB、业务时间、审批脚本；固定模型参数、输出预算、请求/工具执行上限；模型输出即使 temperature=0 也不能视为完全确定。
- 正式建议每独立 Holdout 任务每组 **3 次运行**；若 40 任务×4 组，则至少 480 次任务运行。先估算最坏请求数及费用并获授权，预算不足需缩小**事先声明**的总体设计，而非事后剔除失败项。
- 所有失败、超时、用量缺失和 API 异常均记录；未完成实验标记 `partial`，不能挑成功样本报整体通过率。

### E4. 评测指标及统计

| 指标 | 定义与要求 |
|---|---|
| Business Outcome Success | 最终业务状态满足后置条件的运行比例；独立于回复是否出现关键词 |
| Safety/SOP Compliance | 按适用任务逐规则统计；不安全副作用的原始次数与比例均报告 |
| Response Fact Correctness | 回复涉及订单/金额/日期/拒绝原因等必要事实是否准确 |
| Full Task Success | Oracle V2 按任务适用规则联合判定；同时保存三层得分 |
| Memory Retention | 早期关键约束在后续决策/业务操作中的正确保持；明确测试分母 |
| Tool/Skill Efficiency | 提议、实际执行、重试、Skill 路由、额外确认与失败恢复分别统计 |
| Provider Tokens | 输入/输出/总量；包含路由与摘要；缺 usage 记 `unknown`，不可填 0 |
| Latency/Cost | 总任务延迟及公开单价下费用估计；缓存、单价/时间口径写清 |
| 成本效能 | 成功任务数/100K 真实 Token，和成功率共同报告 |

- 汇总按**不同 case 分组**；三次重复不当作 3 个独立任务，置信区间宜用 case-level 配对 bootstrap，报告任务数量和差值区间。
- 同时统计全部任务与成功任务的 Token/延迟均值、中位数/P95；避免成功率与成本的幸存者偏差。
- 不因效果不好而修改 Oracle；如发现严重新规则错误，冻结问题并发布补充审计及新版本，旧成绩保持可追溯。

### G-E 验收门槛

- 新 Dev/Holdout、Oracle V2、所有变体配置和安全规则已冻结并有哈希/Commit；可证实 Holdout 未用于开发调参。
- 完整离线回归、数据库副作用/幂等/审批恢复、ToolMessage 协议、Skill Allowlist 测试全通过；不安全副作用为 0。
- 真实付费实验**仅在用户新授权下**进行；没有预算时可完成 E 的离线就绪 Gate，但不得标记 `G-E_REAL_LLM_PASS`。
- 所有完成的结果可以由脚本复算；逐任务结果、失败样本、真实 usage 与配置版本留存。最终至少输出一次集计、一次 case 级配对对照和分类结果。
- 最终成绩可以不提升；**Gate 衡量可验证性、安全性和实验公平性，不以漂亮数字作为通过条件**。

**交付**：`docs/reports/v1_1_e_holdout.md`、`artifacts/v1_1/results.csv`、`holdout_summary.json`、真实调用与费用账本、实验复现命令、失败案例库。无付费授权时相应文件不得虚构。

## 8. 阶段交付与独立审查制度

### 8.1 每阶段必须提供

1. 该阶段 `docs/reports/v1_1_*.md`，含目标、实际实现、未完成项、核心源码文件/函数、设计取舍与已知风险。
2. Git 分支、准确完整 Commit SHA、相对上一阶段 diff、工作树状态、Tag（建议 `v1.1-a`…`v1.1-e`）。不得覆盖旧 V1 Tag。
3. 测试命令、pytest 数量/结果、原 11 场景和 7 开发任务结果、Ruff/CI 结果；CI 未运行必须明确说 `not_run`。
4. Gate 每项逐条 PASS/FAIL 与具体文件、测试名、运行产物的证据。新增测试必须含失败反例，不可只测 happy path。
5. 核心代表性脱敏轨迹或历史 run ID，与分析/判分脚本能对应；不得提交凭据、全量原始用户信息或未脱敏数据。
6. 本阶段代码变更/数据规模、是否符合 `docs/architecture.md` 的目录职责、是否引入不必要抽象。

### 8.2 独立审查与失败处理

- 有子 Agent 时，使用 **Implementation / Reviewer / Test** 三个角色，Reviewer 不直接修改被审代码，Test 独立重跑并验证反例；若无子 Agent，以分离的实现、审查、测试步骤替代，不得虚报独立性。
- 一个 Gate 最多连续 3 轮“审查 → 修复 → 重测”；仍有安全、数据一致性、Protocol 或测量完整性问题必须停止，保留成果并报告阻碍。
- 对普通失败优先修复代码、补回归测试；若实验结果负面，**不视为工程失败**。
- A/B 可连续推进，C/D 只能在上一阶段验收后继续；E 的真实付费阶段必须另行获得用户预算许可。

### 8.3 交付审查清单

- 原业务语义、退款幂等、HITL、身份隔离和 B1 基线稳定。
- 原始 `V1 frozen` 统计和原 Oracle 只读；V1.1 V2 诊断标注后验，不混为正式独立测评。
- 分层 Memory 只将可信状态投影给 LLM，完整审计事实不丢；Context 不破坏工具消息配对。
- Skill 策略在执行层强制权限，路由/摘要消耗计入总成本；默认推荐策略由 Dev 决定并有完整记录。
- 新数据存在独立任务、冻结证据、泄漏审计；评测结果可复算，失败样本完整保留。
- README / 面试指南写清楚“原仓已有功能 vs 本项目新增贡献”“真实结果 vs 目标”“合成长历史 vs 真实多轮历史”；不能声称生产级系统。

## 9. 推荐执行次序与停止条件

```text
Phase A 代码/CI同步 + Oracle V2 + V1历史审计
       ↓ G-A 本地通过（远端CI交付问题单列）
Phase B Token成本 / 失败轨迹归因
       ↓ G-B 通过
Phase C Memory/Context 因素消融与轻量优化
       ↓ G-C 通过
Phase D Skill 路由诊断与按条件优化
       ↓ G-D 通过
Phase E 数据冻结、离线评测就绪
       ↓ 若需要真实DeepSeek评测，先获取用户明确预算授权
Phase E 实际线上配对评测 + 最终独立审查
```

**必须立即停止而不是强行继续**：凭据泄露；业务副作用不幂等；未审批真实副作用；Tool Call/ToolMessage 协议破坏；旧冻结数据被改写；Holdout 发生开发数据泄漏；三轮修复仍无法通过关键 Gate；无法执行付费上限却准备运行 API；Git 操作可能破坏不可恢复的历史。

**最终项目状态应按实际写明**：`V1.1_ENGINEERING_READY`、`V1.1_EVAL_READY`、`V1.1_REAL_EVAL_COMPLETE`、`BLOCKED`，不得把离线通过等同在线效果验证。
