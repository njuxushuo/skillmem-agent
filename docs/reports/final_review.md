## 2. 实际架构与来源边界

当前应用为**19个Python文件、4056物理行**，包含注释和空行。唯一应用包仍为`support_agent`；没有Java代码、多Agent运行时、SFT/RL、向量数据库、独立Planner或LLM摘要模块。应用规模超过最初约2000行的轻量估计，文档已承认这是可靠执行和评测扩展的维护代价；尤其`evaluation.py`较大，不应宣传为最小示例。

核心链路与源码一致：

```text
CLI / FastAPI
  → SupportService：客户/会话归属、串行、执行预算、审批与恢复
  → StateGraph.agent：按变体构造模型上下文
  → 同一模型：普通答复，或工具提议
  → guarded_tools：ID/参数/单调用/预算/Skill允许列表
  → ToolNode：原业务工具 → Policy → Store事务/回执
  → M/MS observe：可信结果更新任务状态 → 下一轮agent
```

| 模块 | 已验证职责与边界 |
|---|---|
| `service.py`、`execution.py` | 会话与审批编排；本机POSIX锁、持久计数和协作截止；不是分布式调度或账户级通用费用控制 |
| `store.py`、`tools.py`、`policy.py` | SQLite业务快照/回执、工具入口重验、审批恢复；业务与checkpoint不是同一事务，以稳定回执应对重放 |
| `state.py`、`memory.py` | JSON友好任务投影，用户约束与可信工具事实分开；来源及订单边界明确，不是长期画像或通用语义记忆 |
| `context.py` | 成组保留工具请求/结果，确定性投影与裁剪；保留完整checkpoint；预算是保守估算，不是计费tokenizer |
| `skills.py`、四份SOP、`graph.py` | 同一模型select_skill、下一轮动态Schema、执行层再次允许列表检查；初始化读全部SOP，按需披露发生于模型输入 |
| `evaluation.py`、`tracing.py` | 单一Oracle、隔离夹具与任务runner、真实事件与用量；离线/Mock/provider严格区分 |
| `run_benchmark.py`及共享预算transport | 仅用于受限实验的冻结、预留、调度和导出；4线程是互相隔离的case调度，不是业务多Agent |

Stage5相对Stage4的应用改动仅在`evaluation.py`，净增485物理行；Stage4的Graph、Service、工具、Policy、Memory、Context与Skills没有为Final改动。54个冻结文件的manifest在最终审查时再次通过；从实验提交到当前不存在冻结源码、脚本、测试、数据或依赖锁的变化。

原始8工具与业务来源明确。`LICENSE`和`policy.py`均与原始上游逐字节一致；README保留原作者Nitanand Singh及MIT来源，并说明OWWZO仅为思想参考、没有复制Java架构。不得把原Agent Loop或原工具全部描述为本项目从零开发。

中文`1002号订单`导致数值匹配失败，是已确认的Oracle缺陷，不是模型没认出订单；安全拒绝词表也不完备。原始源码、评分与哈希均保留，没有通过看过Final再修Oracle、重标主成绩或重跑模型追求通过率。公开[oracle_audit.json](../../artifacts/oracle_audit.json)保留逐行独立标签与原hash。

成功样本的语义假阳性没有被穷尽审查，因此不能把原分数简单称为真实成功率严格下界。Memory指标也受最终文字输出条件影响。SOP100%只指适用退款提议前有成功资格查询，分母因模型是否提出退款不同，不等于四份SOP全面合规。
